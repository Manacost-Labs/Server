# Manacost Labs · Skills & AI Engineering

Единый каталог навыков и инженерных правил для AI-агентов на Debian-сервере.
Репозиторий связывает **общую политику, выбор навыков и моделей, проверку изменений
и безопасную работу нескольких сессий** — без загрузки всего каталога в каждый запрос.

[Правила агента](AGENTS.md) · [Руководство](docs/engineering-system.md) ·
[Подключение клиентов](docs/agent-entrypoints.md) ·
[Экономия лимитов Codex](integrations/codex/subscription-savings/README.md) ·
[GitHub CI](https://github.com/Manacost-Labs/skills/actions/workflows/verify.yml)

## Что здесь есть

- **Один источник правил:** серверные и поддерживаемые клиентские точки входа
  ссылаются на [AGENTS.md](AGENTS.md).
- **Навыки по задаче:** профили помогают выбрать небольшой набор канонических
  `SKILL.md`, а не добавляют весь каталог в контекст.
- **Роли моделей:** ведущий, разведчик контекста, ограниченный исполнитель
  и независимый ревьюер с проверкой доступности в конкретном клиенте.
- **Проверки по риску:** LOW → MEDIUM → HIGH → CRITICAL; подсказка не может
  понизить обнаруженный уровень риска.
- **Один вход в качество:** `make verify` локально и в GitHub Actions.
- **Scope Guard:** явные границы задачи и обнаружение конфликтующих изменений
  между сотрудничающими сессиями.

Это каталог и набор инструментов, не фоновый сервис и не универсальный
принудительный контроллер всех AI-клиентов. Он не удаляет старые skills,
не мигрирует приложения и не меняет production-копии автоматически.

## Экономия лимитов ChatGPT/Codex

Сервер использует несколько независимых уровней: RTK сокращает шумный вывод
команд, ObservationPack архивирует слишком большие текстовые tool results с
точным локальным recall, budget gate ограничивает handoff-пакеты, минимальные
профили не загружают лишние MCP, model routing не запускает старшую модель без
обоснования, а compact-plus сохраняет состояние вокруг compaction. Отдельный
usage monitor измеряет результат, но сам лимиты не уменьшает.

Переносимые скрипты, пример hooks-конфигурации, фактические измерения,
ограничения, безопасность и откат подробно описаны в
[руководстве по экономии лимитов](integrations/codex/subscription-savings/README.md).
Процент сокращения tool output нельзя считать тем же процентом экономии общего
лимита подписки: это только одна часть полного модельного контекста.

## Быстрый старт

### На этом сервере

Каноническая рабочая копия уже находится в `/srv/projects/tools/skills`:

```bash
cd /srv/projects/tools/skills

# Проверить политику и посмотреть назначение моделей
./scripts/skillctl validate-policy
./scripts/skillctl models

# Выбрать навыки для конкретной задачи
./scripts/skillctl route . --profile server \
  --task 'Обновить документацию репозитория' \
  --skill engineering/addy/documentation-and-adrs

# Проверить код каталога и отдельно — установленные серверные ссылки
VERIFY_RISK=HIGH make verify
make entrypoints
```

`models` только разрешает идентификаторы из конфигурации: команда не запускает
модели и не переключает текущую сессию. `route` возвращает пути к навыкам;
агент должен прочитать выбранные файлы и применить их.

### Экономный runtime dispatch (opt-in)

```bash
./scripts/skillctl dispatch . --task 'Проверить изменение' --risk HIGH
./scripts/manacost-dispatch . --task-file /private/task.txt --risk HIGH
```

Это только JSON-план и точный argv, без запуска. LOW/MEDIUM идут к роли worker
с Medium reasoning; HIGH — scout → lead → независимый high_reviewer,
CRITICAL — с critical_reviewer. Architect используется отдельным этапом,
а не постоянным исполнителем. `max`/`ultra` автоматически запрещены.
Без подтверждения доступных моделей/effort план не исполним. Фактический запуск
требует `--execute`, выбранный этап и приватный журнал попыток; повторные попытки
и fallback обязательного reviewer запрещены. Глобальный `config.toml` и модель
текущей сессии не меняются. Старый `route` полностью сохранён.
Подробности, лимиты и честные ограничения — [model routing](docs/model-routing.md).

### В отдельной проверочной копии

Основная версия каталога находится в ветке `main`:

```bash
git clone --branch main \
  https://github.com/Manacost-Labs/skills.git
cd skills
make test-portable
```

Для переносимых проверок нужны Linux, Bash, Git, Make, Python 3.11+,
ripgrep и стандартные GNU-утилиты. Полный `make verify` дополнительно использует
Ruff, ShellCheck, Actionlint и Gitleaks. Проверенная установка инструментов
описана в [CI workflow](.github/workflows/verify.yml); основной Python-код
использует стандартную библиотеку.

Не запускайте установщики серверных ссылок из временного клона:
они подключают именно тот checkout, из которого были запущены.
`make entrypoints` предназначен для канонической копии на этом сервере,
а не для GitHub runner или произвольного ноутбука.

## Как проходит задача

1. Агент читает применимые правила, фиксирует состояние Git и границы задачи.
2. Выбирает профиль, оценивает риск и загружает только нужные skills.
3. Для нетривиальной работы получает краткий контекст; использует существующую
   карту Graphify и точечную навигацию, если они доступны и полезны.
4. Выполняет ограниченные изменения, проверяя чужие и защищённые пути.
5. Запускает тесты и `make verify`; получает независимое ревью, когда его
   требует риск или изменение глобальной архитектуры.
6. Сообщает фактические результаты. Commit, push и deploy требуют разрешения
   в задаче; наличие skill само по себе такого разрешения не даёт.

Приоритет правил: **system/platform → developer/security → явный запрос
пользователя → project AGENTS → global AGENTS → профиль → skill**.

### Роли моделей

| Роль | Назначение |
| --- | --- |
| Sol | Повседневный ведущий: реализация, контракты, интеграция; HIGH-ревью |
| Luna | Краткая разведка контекста; необязательное MEDIUM-ревью |
| Terra | Чётко ограниченные, независимые исполнительские задачи |
| Astra | Глобальная архитектура, сложная эскалация и CRITICAL-ревью |

Идентификаторы не дублируются по конфигурациям:
[таблица моделей](skills/engineering/synthesis/synthesis-model-tiers/tiers.yaml)
— источник для `skillctl models`. Назначения ролей, критерии риска и бюджета
контекста находятся в [engineering.json](policies/engineering.json).
Клиент должен реально поддерживать и запускать выбранную модель; подмена
обязательного ревью недоступной модели не считается успешной проверкой.

### Профили

| Профиль | Для каких задач |
| --- | --- |
| `server` | Общая работа на сервере и координация; включает `engineering` |
| `engineering` | Архитектура, реализация, отладка, тесты и доставка |
| `openbot` | OpenBot и интерфейс чата |
| `hearthpulse` | Сервисы HearthPulse |
| `wordpress` | WordPress-сайты и плагины |
| `data` | Парсеры, данные и Python |

Профиль — каталог доступного, не пакет обязательной загрузки.
Ориентир: 0–1 skill для простой задачи, 1–3 для обычной, до 4–5 для сложной.
Внешние каталоги остаются зависимостями со своей provenance и лицензиями;
различающиеся версии не объединяются молча.

## Проверки и команды

| Команда из корня каталога | Что она проверяет или возвращает |
| --- | --- |
| `make verify` | Применимые проверки по риску текущих изменений |
| `VERIFY_RISK=HIGH make verify` | Полный HIGH-набор проверок этого репозитория |
| `./scripts/skillctl verify . --dry-run` | План проверок и полноту необходимых категорий |
| `make test-portable` | Реестр и существующие контракты CLI без серверной установки |
| `make test` | Дополнительно серверные интеграционные тесты Graphify и graph portal |
| `make entrypoints` | 10 ссылок на политику и отдельный адаптер Cursor |
| `./scripts/skillctl list engineering` | Доступные навыки профиля без их активации |
| `./scripts/skillctl resolve data/test-driven-development` | Путь к одному каноническому skill |
| `./scripts/skillctl plan /path/to/project` | Профиль и план подключения без изменений |
| `./scripts/skillctl audit /path/to/project` | Совпадения и расхождения локальных копий |
| `./scripts/skillctl check-response < response.md` | Формат итогового ответа агента |

HIGH-набор включает валидацию политики и реестра, тесты маршрутизации,
интеграционные тесты Scope Guard, регрессии проверки секретов, Ruff,
ShellCheck, Actionlint и сканирование изменённых файлов Gitleaks.
Точный состав задаёт [.ai/verify.json](.ai/verify.json).

GitHub Actions запускает ту же команду с `VERIFY_RISK=HIGH` и базовым
коммитом события. Для воспроизведения конкретного CI-сравнения:

```bash
VERIFY_RISK=HIGH VERIFY_BASE=<base-commit> make verify
```

Отсутствующий инструмент, таймаут или упавшая проверка — ошибка, не PASS.
Сканируются полные изменённые файлы и отдельно подготовленные в Git версии;
это не полный аудит истории или доказательство отсутствия всех секретов.
Серверные графовые тесты требуют реального окружения Graphify и проектов;
переносимые проверки не доказывают работу опубликованного графа.

## Что применяется на сервере

Серверные точки входа:

- `/srv/projects/AGENTS.md`
- `/home/debian/AGENTS.md`
- `/home/debian/server/AGENTS.md`

Клиентские точки входа настроены для Codex, OpenCode, Claude Code, Gemini CLI,
DeepSeek Harness, Hermes Agent и Cursor. Полный список путей, установка,
обратимые резервные копии и ограничения:
[agent-entrypoints.md](docs/agent-entrypoints.md).

Изменение канонического файла видно через ссылки сразу. Но уже открытая сессия
может сохранять прежний контекст: для применения новой редакции её нужно
перечитать или начать новую сессию. Проверка ссылок не подтверждает, что
конкретный клиент действительно загрузил и соблюдает правила.

У Hermes обнаружение `~/.hermes/AGENTS.md` зависит от рабочего каталога;
`SOUL.md` остаётся отдельным файлом личности. Для Cursor установлен адаптер
с `alwaysApply: true`; его загрузка зависит от поддержки механизма правил
клиентом. Ближайшие project/vendor policy-файлы сохраняются.

Общая политика доступна через установленные точки входа, но проектные
`make verify`, CI и перенос локальных skills подключаются **по одному проекту**.
См. [подключение проверок](docs/engineering-system.md#project-opt-in-without-replacing-existing-gates)
и [миграцию](docs/migration.md).

## Работа нескольких сессий

До начала изменений создайте уникальный scope с точными разрешёнными путями.
Полный пример команд:
[Scope Guard](docs/engineering-system.md#scope-guard-and-parallel-sessions).

Guard обнаруживает пересечения заявок, изменения защищённых файлов,
подготовленные изменения и дрейф после контрольной точки. Он не является
sandbox или атомарной блокировкой от любого процесса. Для параллельной записи
предпочтительны отдельные Git worktrees; исходные незавершённые изменения
считаются защищёнными.

## Устройство репозитория

```text
AGENTS.md                       глобальная инженерная политика
policies/engineering.json        роли, риск и требования к проверкам
profiles/                       доступные наборы навыков по типам проектов
skills/                         канонические навыки с метаданными
registry.yaml                   машинный реестр и внешние каталоги
inventory/                      исходные пути, provenance и хэши
scripts/skillctl                 единый CLI
scripts/engineering.py          маршрутизация и запуск проверок
scripts/scope_guard.py          границы задачи и защита параллельных сессий
scripts/check_changed_secrets.py проверка изменённых файлов и индекса Git
.ai/verify.json                 проверки именно этого репозитория
.github/workflows/verify.yml     тот же make verify в GitHub Actions
integrations/                   адаптеры клиентов
tests/                          регрессионные и интеграционные тесты
docs/                           руководства, аудит и операции
```

Каждый канонический навык содержит `SKILL.md` и `skill.yaml` под
`skills/<namespace>/<skill-id>/`; namespace может быть вложенным.

## Как внести изменение

Прочитайте [AGENTS.md](AGENTS.md), проверьте состояние Git и владение путями.
Меняйте канонический файл, а не отдельную копию в клиентской директории.
Сохраняйте метаданные, namespace и происхождение импортированных навыков.
При изменении поведения добавляйте содержательные регрессионные тесты.

Перед публикацией выполните `VERIFY_RISK=HIGH make verify`; при изменении
серверного подключения также `make entrypoints`. Не выключайте падающие
проверки и не добавляйте секреты, production-данные или сгенерированные кэши.
Удаление старых копий — отдельный согласованный этап после проверки проекта.
